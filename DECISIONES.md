# Decisiones · Parte A

1. Python 3.11+ con biblioteca estándar para HTTP/SQLite y tres dependencias funcionales (`phonenumbers`, `jsonschema` y `truststore`), con versiones de dependencias transitivas fijadas. La dependencia fijada `rpds-py` exige Python 3.11+. Base local persistente, sin alta disponibilidad ni servicios de pago obligatorios.
2. La política concreta de Parte A prevalece sobre la anticipación: basta teléfono **o** correo válido; nombre vacío y mensaje vacío se conservan. Un contacto ausente o inválido se marca; sin ninguno válido se rechaza de forma revisable, sin borrar.
3. Para números sin indicativo internacional se asume Ecuador (`DEFAULT_PHONE_REGION=EC`) por el origen de las campañas. Es una decisión posterior al planteamiento de Fase 1, donde se propuso no asumir país por ciudad. Se conserva el original y el supuesto se puede cambiar. Los prefijos internacionales explícitos siempre se respetan; no se reescriben a +593.
4. Se acepta teléfono entero JSON, no booleanos ni flotantes. Ciudad con una única cadena en una lista se normaliza; otros tipos inesperados se marcan sin convertir objetos en texto para el modelo. No se exige verificación DNS porque una comprobación transitoria no debe descartar un paciente y los ejemplos usan dominios ficticios.
5. Identificadores faltantes, JSON malformado y estructura inválida se guardan como rechazados, con referencia interna, y reciben 202 **solo tras persistencia** para no agotar reintentos inútiles. Un conflicto de contenido con igual `event_id` conserva el original y la entrega conflictiva para revisión.
6. Idempotencia por `event_id` y deduplicación de contacto son distintas. Para unir nuevos eventos se requiere nombre compatible más contacto dentro de 30 días. Si falta nombre o hay varias coincidencias, se conserva separado antes que fusionar familiares. La regla no verifica identidad para permitir revelar datos a terceros; no se envía historia al paciente ni al LLM.
7. Se recorren todas las páginas de pacientes y tratamientos; se conserva progreso mínimo. Tratamientos `pendiente` y `en_curso` se consideran trabajo pendiente a efectos de priorización. Una consulta fallida nunca se registra como paciente inexistente.
8. El LLM interpreta el mensaje y produce JSON validado; reglas locales protegen señales explícitas. La intención de tratamiento de alto valor requiere compromiso en el mensaje, no únicamente el servicio seleccionado. Spam requiere evidencia clara, y la inyección no puede elevar prioridad por sus propias instrucciones.
9. El usuario proporcionó credenciales y eligió inicialmente Gemini `gemini-3.8-flash` y Telegram. Las credenciales se guardaron exclusivamente en `.env` local excluido de Git. El token de pacientes corregido autentica correctamente. La generación de 3.8 devolvió 503 por alta demanda. Posteriormente el usuario autorizó buscar y cambiar a un modelo disponible usando la misma clave: se seleccionó `gemini-3.5-flash-lite` después de consultar modelos accesibles y probarlo. La clasificación real y el flujo de los diez payloads ya completaron correctamente. No se presumen créditos gratuitos ni disponibilidad futura garantizada.
10. El 18/10/2026 solicitado por el usuario se conserva como fecha de ejemplo, sin confirmar una cita dominical. Faltan horarios, duraciones y enlace de agenda en los materiales recibidos. Un enlace real configurable resuelve la propuesta sin inventar disponibilidad; su ausencia se declara como pendiente de cumplimiento.
11. Los mensajes al paciente solo se redactan. Las notificaciones operativas no contienen datos de contacto ni datos clínicos; su referencia apunta al registro local. Se conserva el original en SQLite para recuperar y auditar, con permisos de acceso restringidos fuera del repositorio.
12. Reintentos técnicos limitados con espera creciente; 401/400/404 no se repiten automáticamente. 429 respeta la espera y no consume el presupuesto de intentos: el watchdog hace visible la demora. La recuperación manual conserva la misma identidad del evento y vuelve a la etapa fallida.
13. Aviso preliminar para intención caliente evidente, independiente de la API y del LLM. Los casos calientes descubiertos solo por historial dependen de la latencia y límite de la API. Se declara el riesgo del plazo ante picos y caídas; no se simula una garantía imposible.
14. No se implementan conciliación automática con Meta, segundo canal de avisos, alta disponibilidad, firma de conector inexistente ni agenda clínica. Los avisos por silencio requieren configuración operativa, por eso no se activan indiscriminadamente.
15. Las pruebas usan dobles de terceros y los diez JSON originales. Sus respuestas de pacientes son fixtures para probar escenarios; no se presentan como evidencia del servicio real. El verificador HTTP separado permite ejecutar los mismos originales con proveedores reales.
16. El brief pide publicar en un fork. El usuario creó `https://github.com/josuealejandroma-web/cerro-alto-leads` y autorizó subir la implementación. Se publica el código conservando el historial y los payloads del repositorio base, sin credenciales ni datos de ejecución. No se pulsa “Entregar Parte A” porque congela la entrega e inicia la ventana siguiente.
17. El TLS inicial de Python no confiaba en la cadena recibida de Telegram. Se incorporó `truststore` con el almacén de confianza nativo del sistema, sin desactivar validación de certificados ni de host. Se añadieron dos pruebas de estas garantías y de la propagación controlada del error TLS.
18. Se verificaron siete ejemplos contra la API real de pacientes: los eventos 06 y 09 identificaron un paciente con tratamiento pendiente; los otros cinco no encontraron coincidencias. La comprobación se limitó al enriquecimiento, sin enviar historial al LLM. En un intento controlado del evento 05, el fallo de Gemini quedó recuperable y los avisos de error fueron enviados. El ZIP solo contiene código y evidencia resumida, no bases, credenciales ni respuestas clínicas.
19. El 16/10/2026 se verificó Gemini 3.5 Flash-Lite con casos de contacto solo por correo, texto largo e inyección, y después con dos pasadas completas del verificador HTTP y proveedores reales. Hubo nueve clasificaciones validadas, ningún error del LLM y cuatro avisos calientes enviados en menos de cinco minutos. La API de pacientes produjo dos 500 y una respuesta JSON inválida; los reintentos recuperaron los tres casos y cada incidencia fue notificada. La auditoría exige que no queden errores o pendientes sin resolver, conservando los errores históricos como evidencia.
20. El evento 05 fallido con Gemini 3.8 se reencoló desde su registro persistente y terminó procesado como tibio con el nuevo modelo, sin reenviar el webhook. Se conservan sus avisos históricos.
21. La recepción de Telegram se comprobó con un código enviado por la persona desde el chat configurado: `getUpdates` lo recibió y el bot devolvió una confirmación. Se añadió un diagnóstico reproducible que preserva webhooks y actualizaciones ajenas. No se añadió un chatbot de atención clínica ni procesamiento permanente de todas las conversaciones.
